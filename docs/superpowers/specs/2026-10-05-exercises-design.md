## Назначение и объём

Реализовать справочник упражнений, который используется программами тренировок. В задачу входят ровно пять операций Exercises из Swagger.

| Метод и путь | Доступ | Успешный ответ | Описанные ошибки |
| --- | --- | --- | --- |
| GET /exercises | Авторизованный пользователь | 200, ExerciseListResponse | 401 |
| GET /exercises/{exercise_id} | Авторизованный пользователь | 200, Exercise | 401, 404 |
| POST /exercises | ADMIN | 201, Exercise | 400, 401, 403 |
| PUT /exercises/{exercise_id} | ADMIN | 200, Exercise | 400, 401, 403, 404 |
| DELETE /exercises/{exercise_id} | ADMIN | 204, без тела | 401, 403, 404, 409 |

`exercise_id` в пути соответствует `^[a-fA-F0-9]{24}$`.
При использовании упражнения хотя бы в одной программе удаление возвращает 409, `code: CONFLICT`, `message: Exercise is used in one or more programs`.

## Данные

В MongoDB хранить `_id: ObjectId` и `created_at: Date`. В API возвращать `id` строкой и `created_at` строкой date-time.

| Поле запроса | Требование Swagger |
| --- | --- |
| name | Строка длиной 1–100; обязательна при создании |
| description | Необязательная строка длиной до 500 |
| muscle_groups | Непустой массив MuscleGroup; обязателен при создании |
| equipment | Непустой массив Equipment; обязателен при создании |
| video_url | Необязательная строка формата uri |
| image_url | Необязательная строка формата uri |

MuscleGroup: `CHEST`, `BACK`, `LEGS`, `ARMS`, `SHOULDERS`, `CORE`, `FULL_BODY`.
Equipment: `BARBELL`, `DUMBBELL`, `MACHINE`, `BODYWEIGHT`, `KETTLEBELL`, `RESISTANCE_BAND`, `OTHER`.

В ExerciseUpdateRequest нет required: PUT допускает передачу отдельных полей. Отсутствующее поле сохраняет прежнее значение. Не заменять PUT на PATCH и не делать все поля обязательными. Схема не разрешает null для перечисленных полей; отсутствие optional-поля и null — разные значения. В ответе обязательны `id`, `name`, `muscle_groups`, `equipment`, `created_at`.
Не вводить уникальность названия, новые перечисления или требование уникальных элементов массива: таких ограничений в Swagger нет.

## Список

Параметры: `muscle_group`, `equipment`, `search`, `cursor`, `limit`.
В query имя `muscle_group` остаётся в единственном числе; в документе и ответе поле называется `muscle_groups`.
Массивы фильтра передаются через запятую (`style: form`, `explode: false`). Поиск — по названию и описанию.
Курсор следующей страницы берётся из `next` предыдущего ответа. `limit`: 1–100, значение по умолчанию 20.
Ответ содержит `data`, `next` (строка или null), `limit`, `has_more`.

## Устройство модуля

Следовать заданной архитектуре: `handlers → dtos/services → repositories → MongoDB`.

- `app/handlers/exercises.py`: пять маршрутов, функции `(request, params)`, извлечение значений через `.get()`, валидация в начале обработчика, преобразование результата в ответ API.
- `app/dtos/exercises.py`: dataclass DTO для запросов и проверка типов/ограничений. Для массивов и optional-полей нужна собственная валидация; существующий BaseDTO рассчитан на обязательные строки. Изменение Auth/BaseDTO в объём не входит.
- `app/services/exercises/`: операции справочника и правило запрета удаления используемого упражнения; без роутинга и прямого создания зависимостей.
- `app/repositories/exercises.py`: операции PyMongo и проверка ссылки в `programs.exercises.exercise_id`; зависимости через конструктор.
- `app/errors/exercises.py`: ошибки отсутствующего упражнения и конфликта использования в рамках опубликованных ответов.
- `app/database/validators.py`, `indexes.py`: схема exercises по указанным типам/обязательным полям, запрет лишних полей в БД и необходимые индексы под выбранные запросы. Не добавлять бизнес-ограничений сверх контракта.
- `app/dependencies.py`: сборка зависимостей по примеру Auth. Регистрация обработчиков и необходимые реэкспорты — через существующие `__init__.py`.

Использовать существующие require_auth и require_admin в нужном порядке. Новые механизмы авторизации, изменения токенов и дополнительные библиотеки не входят в задачу.
Ошибки валидации: `{code, message, errors: [{field, message}]}`, сообщения на английском. Остальные ошибки: `{code, message}`.

## Согласованная логика и технические решения для проверки

Пользователь 05.10.2026 согласовал: внутри каждого фильтра совпадение хотя бы с одним значением (OR), между muscle_group и equipment — выполнение обоих условий (AND). Например, CHEST,ARMS и DUMBBELL находят упражнения с гантелями на грудь, руки или обе группы. Это согласованное уточнение, а не цитата Swagger.

Следующие детали не заданы в Swagger; явно включены в подтверждённый пользователем план как минимальная реализация существующих операций:

- Поиск: буквальная подстрока в name или description без учёта регистра. Пользовательский текст не исполняется как регулярное выражение; никаких дополнительных режимов поиска.
- Пагинация: стабильный порядок по _id по возрастанию. next — строковый ObjectId последнего выданного упражнения, только если существует следующая страница; иначе null. Запросить limit + 1 документов для вычисления has_more. cursor — не offset; фильтры продолжают действовать на каждой странице. Нового параметра sort нет.
- Некорректные query-параметры возвращают 400 в существующем формате BAD_REQUEST/Validation failed/errors. Этот случай не перечислен у GET /exercises в Swagger: это предлагаемое уточнение обработки неверного запроса, не правка опубликованного файла API.
- Неверный формат ID для GET/DELETE обрабатывается как 404 NOT_FOUND; для PUT — как 400 с ошибкой exercise_id. Корректный, но отсутствующий ID всегда даёт 404.
- При проверке использования упражнения искать programs.exercises.exercise_id как ObjectId и как его строковое представление. Это защищает правило 409 при интеграции с ещё не реализованным Programs и не меняет его документы или API. Пример на скриншоте хранит ObjectId, HTTP передаёт строку, тип вложенного поля в текстовой схеме не указан.
- При создании отсутствующие optional-поля не сохраняются и не подставляются как null. При PUT обновлять только переданные известные поля; пустой объект допустим по опубликованной схеме и возвращает прежнее упражнение. Неизвестные ключи HTTP-запроса не сохраняются в БД: additionalProperties=false задан для БД, но отсутствует в HTTP-схеме.
- Нормализация имени: убрать пробелы по краям по образцу существующих DTO; пустое после этого имя даёт ошибку name cannot be blank, как в примере PUT. Не менять регистр имени и не удалять дубликаты элементов массивов.
- Ссылки проверять как URI со схемой, без добавления ограничения «только HTTP/HTTPS», которого нет в контракте.

Новые функции, поля и методы эти решения не добавляют. План подтверждён пользователем перед реализацией.

## Зависимость от инфраструктуры

В `app/server.py`, метод `_send`, сейчас `body=None` превращается в `{}` и записывается в HTTP-ответ даже со статусом 204. Это препятствует соблюдению DELETE-контракта без тела.
Не менять сервер самовольно: исходная инструкция требует предварительного согласования инфраструктуры. Не обходить проблему заменой 204 на 200 или обходом общего механизма отправки ответа. Нужна отдельная согласованная поправка для 204.
Порт локального сервера 8000 и Swagger 8080 уже отмечены в README_LOCAL; изменение порта не входит в Exercises.
